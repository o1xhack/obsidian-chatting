# Chatting with AI

Agentic AI chat plugin for Obsidian. Simple, mobile-first, three providers (Anthropic + OpenAI + ChatGPT account sign-in).

## Architecture

```
User Input -> Agent Loop -> API Client (stream.ts)  -> Anthropic/OpenAI/Codex
                 |                                         |
            Tool Executor  <---  tool_use response  <------+
                 |
         Obsidian Vault APIs (read/edit/search/create)
```

- **Transport**: HTTP through `requestUrl()`, except chat streaming via the transport module `src/api/stream.ts`: the only place for `fetch` and for Node's `https` (desktop only, loaded at runtime; mobile uses `fetch`; both fall back to `requestUrl()`). The device check (`diagnostics/capability-check.ts`) uses `browserFetch` for its streaming probes only, which test `fetch` itself. The desktop ChatGPT sign-in's callback server is the other Node module (`http`, `auth/chatgptBrowserLogin.ts`). Mobile WebViews enforce CORS, so `fetch` that a provider doesn't allow falls back.
- **Anthropic** uses Messages API with adaptive thinking and prompt caching
- **OpenAI** uses Responses API with `previous_response_id` for multi-turn
- **ChatGPT account** uses the ChatGPT/Codex backend with Device Authorization Flow credentials in `SecretStorage`
- **Agent loop** is provider-agnostic: send -> tools -> send -> done
- **UI** is a single Svelte 5 component (`ChatContainer.svelte`) mounted in an `ItemView`

## Key Patterns

- **KV cache optimization**: System prompt is static (never includes dynamic context). Only the vault's root `AGENTS.md` and its skills list (names and descriptions) join it (read each turn; they change only when the user edits them, so the cache holds). Dynamic context (active file, selection) goes in the user message after the cached prefix.
- **Vault instructions (`AGENTS.md`)**: The user's vault, not this repo. A folder's `AGENTS.md` is appended to the first tool result of the conversation that touches a file in that folder or below (outer folders first); trusted `instructionSources` metadata records delivery in retained history, so it comes once per conversation and again after a cut. User, vault and tool text cannot forge that metadata. Initial selected text, linked files and invoked Skills include their file paths in instruction discovery.
- **Anthropic `cache_control`**: Breakpoints on system prompt and last tool definition.
- **Thinking level from the model catalog**: The setting offers the levels the catalog lists for the selected model (Codex `supported_reasoning_levels`, Anthropic `/v1/models` `capabilities.effort`); Anthropic's thinking mode comes from `capabilities.thinking.types`. Without catalog data the previous rules apply: Anthropic thinking by model name, Codex `medium` for reasoning models, and OpenAI API-key requests `medium` for reasoning models (its model list has no levels).
- **Per-provider API keys**: Stored as `chatting-with-ai-api-key-anthropic` / `chatting-with-ai-api-key-openai` in `SecretStorage`.
- **In-memory chat persistence**: The agent loops and the conversations live on the plugin instance, surviving view open/close cycles. `chatHistory` is the active conversation's; each conversation's agent loop (`agentFor`) holds its API history, copied into its record when saving or switching.
- **Selection scope**: Injected into user message with scoping instructions, and enforced by `executeTool` for that turn: in the selected note only `edit_document` `find_replace` inside the selection (located by its offset and in-memory editor snapshot; changes outside the range can relocate it, while changed or ambiguous selections are refused) succeeds; other changes to that note, or renaming/deleting a folder it is in, are refused. Other notes stay editable.
- **Conversations**: One `AgentLoop` per conversation that is open or running a turn (`plugin.agentFor`; `plugin.agent` is the open one's). A turn keeps running when the user starts a new chat or switches: `chat-view.ts` keeps a `RunningTurn` per conversation (`turns`) and writes to the chat only while it shows that conversation (`shownChat`). Going back shows the turn as far as it got and asks a waiting `ask_user` question there; the chats list shows "Answering…" (`ConversationSummary.running`, `updateConversations`); a notice says when a background turn has a question or is done; messages added after its last step run when its chat is shown again (kept with it until then, also when saved: `pendingMessages`). Deleting a conversation stops its turn; closing the view stops all. A turn is current while it is its conversation's entry in `turns`: Stop, Clear, edit and delete remove it, and a stopped turn that ends late adds nothing (its `ask_user` answer is empty, a late error is dropped). `activate()` drops the idle loops of conversations left (their history is in the record); a new loop imports the record's API history as a new array, so `previous_response_id` never crosses conversations. A message still in its preflight (linked files being read) or an edit not yet answered is stopped by a switch or a new chat instead and goes back to the input, with what was typed meanwhile, filled in after the next chat is shown so its attachments stay (`cancelPreflight`); the edit's original turn comes back (`RunningTurn.rollback`, also in a background conversation). At start only the open conversation's file is read; the others are `unloaded` (their index entry only) until opened (`plugin.openConversation` reads the file through `loadConversation`, keeping the index's title, so a rename of a chat not read yet stays; one that can't be read leaves the list), so opening, renaming back to the automatic title and deleting are asynchronous. The title is the first user message (40 characters) until renamed. Automatic title/source metadata survives persistence caps, so trimming the original turn does not rename the chat after reload or append. An empty conversation isn't listed and is dropped when left. Exact saved snapshots of idle inactive chats can be unloaded to bound attachment memory without rewriting their files; savedMessages also releases their payload references.
- **Panel layout**: The chat view turns off Obsidian's `.view-content` padding and scrolling (`styles.css`) and pads its own parts. On desktop it keeps the bottom padding, which keeps it clear of the status bar (not needed in the left sidebar). In the phone sidebar it keeps 24px for the tab menu's fade below and turns off the 48px fade over the view with the floating navigation; Obsidian doesn't shrink the sidebar for the keyboard, so `chat-view.ts` measures how much of the view the keyboard covers and lifts the chat by that (`--ochatting-lift`). The safe area is left to Obsidian's containers.
- **Selection history**: Only active turns keep the full note snapshot. UI/saved history keeps a SHA-256 fingerprint; editing/regenerating refuses scoped changes if that note has changed. Older snapshots are compacted on restore.
- **Turn IDs**: Each user turn has an ID on its `chatHistory` entry and on its first message in `AgentLoop` (`ask_user` answers have none). Editing a message or regenerating the last answer cuts both histories just before that turn (`cutBeforeTurn`; a new array, so OpenAI replays it in full) and runs the turn again with its images and selection; only a turn the API history holds after its last compaction can be (`editableTurn`). Rejected edit/regenerate preflight restores the original visible/API histories and pending undo notes; the cut is not saved prematurely. Chats saved before turn IDs get them in the one-time migration of `chat-state.json` (`assignLegacyTurnIds`, only while no turn has one).
- **Images in tool results**: `ToolResult.images` (`view_image`, `view_canvas`) go to the model inside the tool result (Anthropic image blocks; OpenAI and ChatGPT `function_call_output` as an `input_text` + `input_image` list). Only the agent history keeps them; the chat view and its saved `chatHistory` get the text and "[1 image prepared for the model]". Requests leave out tool images older than the last 2 user turns and cap the remaining tool images to the newest 4 fitting 10 MiB, with a note for omissions (`withoutOldToolImages`); OpenAI breaks previous_response_id chaining whenever images are omitted so server context is pruned too; the agent applies the same budget after each tool result and on restore so memory/saved state stay bounded; user attachments stay.
- **Cross-conversation attachment retention**: `attachment-history.ts` bounds attachment data across all chats to 32 MiB of conservatively counted JSON bytes before serialization and on restore. Current chat, then most recently used chats, retain their newest payloads first. Older payloads become named omission text/API blocks and metadata-only UI chips; conversation text and entry identities stay. The same budget includes legacy visible-only blobs. In-memory histories and mounted thumbnails release expired data too. An in-flight request loses its outer-array response cursor after pruning, so its eventual response cannot re-establish stale chaining. With a file per chat (version 4) it counts the chats in memory (the open one, those running a turn and those read since the start); a chat unchanged since it was read or saved (`savedMessages`) is counted first and never stripped, so opening an old chat doesn't change its file, and a chat not read yet keeps its file as saved.
- **Saved chat format**: Version 4: `chat-state.json` is the index, `{ version, savedAt, activeConversationId, conversations: [{ id, title, automaticTitle?, titleSourceTurnId?, customTitle, createdAt, updatedAt, size?, metadataSavedAt? }] }`, and each conversation has its file `chats/<id>.json`, `{ version, savedAt, conversation: { id, title, customTitle, createdAt, updatedAt, chatHistory, agentMessages, notes?, pendingMessages?, pendingTurn?, usage? } }`. Each file is written twice, its `.next.json` copy first, and loading takes the newer whole copy; a save writes only the chats whose content changed (`savedChats`, a digest of each file's JSON, not a copy), then the index; `size` is the chat file's size in bytes (a chat over 5 MB shows it in the chats list, `LARGE_CHAT_BYTES`; the *Saved chats* setting shows the total). A chat file the index doesn't list (Obsidian ended between the two) is added back on load (`addUnlistedChats`), also when `chat-state.json` was kept aside as unreadable; a deleted chat's files are marked deleted with a newer `savedAt` before the index drops them, then removed; a deletion is forgotten only once its file is marked, so a failed save leaves it for the next one. Chat IDs name files: letters, digits, `_` and `-` only (at most 128 characters) (`CHAT_ID`), checked with the index and when splitting a version 3 file. A chat file that can't be read is kept aside as `chats/<id>.corrupt-<time>.json`; one from a newer version is left as it is. The index and the chat files are checked like the whole saved chat was (`isPersistedChatState`, `isChatFile`). Each file keeps the whole visible history and the API history from its last compaction on (`fromLastCompaction`). A file without a version is version 1. Older formats are migrated once on load (`migrateChatState` in `src/chat-state.ts`; 2 → 3 makes the single chat the first, active conversation; up to version 3 every conversation was in `chat-state.json`): the save right after loading writes the chat files and the index, the old file kept as `chat-state.v<version>-<time>.json` first. Title metadata uses per-entry metadataSavedAt so an unrelated index save cannot overwrite newer per-chat titles after an interrupted save; later custom renames win while the file retains automatic-title provenance. A failed backup prevents migration and all saves until restart. Either future-format chat copy is preserved regardless of its timestamp. A chat file already there for a conversation of the old file (a version 4 chat that went through an older version and back) is taken for an empty record and copied aside before it is replaced otherwise (`adoptChatFiles`). A newer version than the plugin knows (saved by a later release, before a downgrade) isn't read: it is copied to `chat-state.v<version>-<time>.json` and the chat starts empty, so the next save doesn't overwrite it. Image data is saved only in the API history; the visible history keeps each image's ID, name, type and size and gets the data back by ID on load (`restoreImages`). An image the API history no longer holds shows as a chip with its name and isn't sent again on edit or regenerate.
- **Follow the AI's edits**: `edit_document`, `set_properties`, `create_file` and `edit_canvas` return `ToolResult.focus`: the changed range in the note (a before/after comparison in `withChange`) or the changed canvas cards. The chat view takes it off the result before showing and saving it; it never goes to the model. With the setting on, `ui/show-in-view.ts` opens the spot through Obsidian's search-match ephemeral state, in the tab that already shows the file or one reused follow tab, without taking the focus from the chat (on a phone the note stays behind the chat). On a canvas it then selects and centers all changed cards through the canvas view's internal API, checked first; without it the match state's select-and-pan stays. The follow tab closes when the plugin unloads; its ID is kept with `saveLocalStorage`, so a tab the saved layout brought back is closed at the next start.
- **Mentions**: `@` or `[[` in the input offers vault files (`src/ui/mentions.ts`); the chosen one goes in as a link. On send, `chat-view.ts` reads the files the message links to (`mentionContext`) and `AgentLoop.run` puts them between the context prefix and the message: a note's text (20,000 characters each, 60,000 together), a canvas outline, images as image blocks, PDF and Office files as files, other text files as text; other files by name. The chat and `chatHistory` keep the typed text and original link-resolution source note; edit and regenerate read the files again relative to that source, even after switching active notes or restarting. Legacy turns without a recorded source resolve from the vault root.
- **Undo per answer**: The chat view passes a new `ChangeLog` (`src/tools/undo.ts`) per turn through `AgentCallbacks.changes` to `executeTool`. Edits record their text before and after in `withChange` (the same comparison that gives `focus`); `create_file` records the file and the folders `ensureParentFolder` made, `rename_file` the rename, `delete_file` the bytes of the file or folder before trashing it. Deletion snapshots are committed only after trash succeeds. A turn with changes ends in a `"changes"` entry in `chatHistory` (`turnId`, `files`, `undone`); its log lives only in memory, in `plugin.changeLogs`, a `WeakMap` keyed by that entry, so it belongs to that entry's conversation and goes away with it (clear, edit cut, delete). Undo snapshots coalesce adjacent edits and are bounded to 32 MiB per answer / 64 MiB across live answers; exceeding the budget expires whole logs and changes their rows to kept, never a partial undo. Undo takes the steps back last first, consumes successful steps, and stops on the first failure so retry cannot repeat a successful step; `conflicts()` names files that changed since, and `undo-confirm.ts` asks first. Undo locks sending without clearing the composer or cancelling attachment preparation; a raced submission restores its draft. The model learns of an undo through the conversation's `notes` (saved with it): the next turn takes them into the context prefix of its user message, not the system prompt, and clears them. After a restart the row shows without undo ("kept").
- **Folded steps**: when a turn ends, `ChatContainer.foldTurn` replaces its tool steps, a text that only led into a step and its changes row with one steps row right above the answer (`ui/fold-turn.ts` decides which rows, `foldPlan`); it opens into the steps and the changed files, and keeps undo. The chat view calls it at the end of a turn and for every finished turn in `renderHistory`. A single step without changes stays; an `ask_user` question stays visible. Nothing about it is saved.
- **Files**: PDF, Word, Excel, PowerPoint and text files (attached with the paperclip or by pasting, up to 4 per message and 10 MB each; mentioned; or `read_file` on a PDF or Office file) become a `FileAttachment` (`src/files/attachments.ts`): a `file` content block in the user message, or `ToolResult.files` in a tool result. Each provider gets its own form: OpenAI and ChatGPT `input_file` with inline base64 data (PDF and Office), Anthropic a PDF `document` block and, for Word, Excel and PowerPoint, a text `document` with the text read when the file was attached (`src/files/office.ts`; the ZIP container is read with `DecompressionStream("deflate-raw")` in `src/files/zip.ts`, no library); text files go as text to all. Tool results with files are left out after 2 user turns and capped to the newest 4 fitting 10 MiB (actual bytes and extracted text), in memory, saved state, and requests. The saved `chatHistory` keeps each attached file's ID, name, type and size; data and text stay in the API history and come back by ID on load (`restoreImages`), so the chat files' format is the same with files. Office ZIP unpacking is limited to 64 MiB total and 8 MiB per XML entry, with bounded XML match counts and Word table expansion. Word/PowerPoint extraction accumulates at most 100,000 characters and stops before later slides after reaching its cap; unsafe local extraction keeps the original attachment without text.
- **Text tool history**: Tool results keep at most 100,000 characters each and a shared 200,000-character text allowance plus omission markers. Oversized prefixes are copied so they release the original backing string. This applies to new results, API restore and visible/saved tool rows; Trusted instruction suffixes are recorded separately by offset and retained complete outside the payload allowance, so clipping file text cannot remove first-touch rules or block nested-rule write retries. Legacy clipped results without a recorded suffix lose provenance so a later write discovers real rules again. Filename listings and metadata-cache enumeration report their returned/read paths through internal instructionPaths; get_links includes displayed outgoing targets and linked sources even without cached lines.
- **Request budgets and preflight**: Mixed picked/linked images and files share a 20 MiB encoded budget. Mention resolution checks metadata before loading a document that cannot fit, then counts actual encoded bytes incrementally. Stopping linked-context preflight restores the unsent draft and undo notes synchronously; late completion cannot overwrite a new draft or resurrect cleared/consumed notes. Each provider checks the final serialized UTF-8 JSON against 30 MB. Preflight failure restores the draft and selection without adding a visible-only user turn. `search_vault` returns internal `instructionPaths` for names matched or files read (including non-matches); the loop adds folder rules then strips this metadata from UI/persistence. Folder rename/delete discovers the whole affected subtree and destination scope. Excel extraction validates cell references and bounds expanded cells/text across the workbook.
- **Skills**: The user's vault, the Claude Code / Codex format: a folder per skill in the skills folder (setting `skillsFolder`, default `Skills`) with a `SKILL.md` whose properties give `name` (else the folder name) and `description` (`src/agent/skills.ts`). Each turn `AgentLoop.run` lists names and descriptions in the system prompt, after the built-in prompt and before `AGENTS.md`. `use_skill` returns a `SKILL.md` without its properties (32,768 characters) and lists the skill's other files, which the model reads with the vault tools. Both use_skill and slash invocation discover folder instructions for the skill file and all listed resources, including nested folders. `/name` in a message (at its start or after a space) makes `chat-view.ts` send the skill loaded along with it, before the linked files; typing `/` offers the skills in the mention list. The *Skills* setting lists them (a `list` definition on Obsidian 1.13+, rows in `display()` before) and *New skill* creates one from `SKILL_TEMPLATE`.
- **Streamed answers**: Chat requests ask for `stream: true` (the Codex route always did) and go through `streamSSE` (`src/api/stream.ts`), their body serialized by `serializeRequest` (the 30 MB check) before anything is sent; a URL where `fetch` looked CORS-blocked uses `requestUrl()` for 10 minutes, whose buffered events arrive at once. The adapters rebuild the same `UnifiedResponse` from the events (`collectAnthropicStream`; `collectResponsesStream` for OpenAI and the Codex route, which keeps its endpoint, headers and body), so replay items, MCP calls and the saved history are unchanged. Text deltas go through `AgentCallbacks.onTextDelta` to the chat view, which grows one message (Markdown re-rendered at most every 100 ms) and replaces it with the whole text from `onResponse`; text before `ask_user` is dropped as before. Stop aborts the request and keeps the text shown. A rate limit is retried only while no text is on screen and no MCP call started (`client.ts`, `onServerTool`). A stream that ends before the provider says the answer is complete (`StreamCutError`; also a connection lost after the answer began, `StreamDropped`) is sent again (with the resends after the background, at most twice per turn); no tool of the plugin ran for it. Once the provider started a tool on an MCP server it isn't sent again (`StreamCutError.sideEffects`): that tool may have changed something. On desktop, a request Node's `https` gets no answer for (a system proxy, a certificate only the OS trusts) goes through `requestUrl()`. The SSE parser scans each chunk once (`scanFrom`).
- **Typing while an answer runs**: The input stays usable during a turn; its button is Stop while the box is empty, Send with text. A message sent then is added to the running turn (`addToRunningTurn` in `chat-view.ts`, `AgentLoop.steer()`) and shown as *Queued* above the input (`setQueued`). The loop sends it with its next request, as a text after the tool results (`[The user added while you were working:]`), and reports it through `AgentCallbacks.onSteered`; the chat then shows it as a user message without a turn ID. What the turn had no step left for (`takeSteered()`, or `steer()` returned false; also what arrives during the last step `maxIterations` allows) runs as the next turn; added to a message refused before it was sent, it goes back to the input with that message. Attachments and the selection wait for the next message; Stop, Clear, editing and deleting the chat drop the queue, and it stays with its turn when the user switches (an edit not yet answered is stopped by a switch: its queue goes back to the input with it). A user message with tool results never starts a turn (`startsUserTurn`), so trimming the history can't orphan them.
- **Back from the background**: Obsidian has no lifecycle event, so `src/platform/lifecycle.ts` (`appLifecycle`) follows hints (the document's `visibilitychange`, Capacitor's `pause`/`resume`, the window's `focus` and `pageshow`; `main.ts` starts it, and each hint goes to the debug log) and records when the app went away. Leaving the app saves the chats. Each request has its own abort controller (`AgentLoop.send`). A request that failed while the app was in the background is sent again once it is back (only errors that may not come again: the network, an abort, a cut stream, an error inside a started response, 408, 429 and 5xx; `transient`), from the same history, and the chat shows "Resuming…" (`onResuming`) and drops the failed attempt's text; this and a cut-off stream share `RESUME.perTurn` (2). A `fetch` failing in the background neither falls back to `requestUrl()` nor marks the URL blocked. On mobile (`Platform.isMobileApp`), a request that gets no data for `RESUME.stallMs` (30 s) after the return, or 2 minutes through `requestUrl()`, which delivers only at the end (`RESUME.bufferedStallMs`, `isBuffered`), is given up and sent again (`watchForStall`, `lastChunkAt` in `stream.ts`); a desktop window isn't watched. A running turn marks its conversation (`pendingTurn`: turn ID and start, an optional field of `chat-state.json` version 3, so an older plugin drops it); the mark is cleared when the turn ends or is stopped. Found at the next start with the API history ending in a user message or tool results with that turn the last in it (`owesAnswer(turnId)`; a new message is marked only once it is sent), the chat offers **Continue** (`setContinue`), never automatically: `AgentLoop.continueTurn()` runs the loop on the history as saved, with no new user message and without running saved tool results again. A new message, Stop, Clear or leaving the chat dismisses it.
- **MCP servers through the provider**: Remote servers only, no MCP client in the plugin (`src/api/mcp.ts`). The settings keep a list (`mcpServers`: name, public https address, on/off; a `list` definition on Obsidian 1.13+, rows in `display()` before); each token only in `SecretStorage` (`chatting-with-ai-mcp-<id>`, `mcpSecretKey`; `removeMcpServer` clears it; a save writes only tokens this device has, so one that didn't load isn't overwritten), never in `data.json`. Requests with an API key name the servers that are on: Anthropic `mcp_servers` with one `mcp_toolset` each and the `mcp-client-2025-11-20` beta header, OpenAI one `mcp` tool each with `require_approval: "never"`. The provider lists and calls the tools; the adapters read the calls from the answer (`mcp_tool_use` / `mcp_tool_result` blocks, `mcp_call` items) into `UnifiedResponse.serverCalls`, and `AgentLoop` shows each as a tool step (`mcp:<server>:<tool>`, "Used create_issue on linear"), never runs it. Replay is bound to hashed server ID/endpoint/authorization identities; changed or disabled servers lose native calls and tool lists, and OpenAI also drops its cursor. Remote result text shares local tool budgets; non-text MCP results are omitted from replay with a note. Results are clipped like tool text (`withBoundedServerResults` in `withoutLargeToolText`; the step shows the clipped result too). Not for the ChatGPT account (its route doesn't offer it) or the Test buttons. New servers start disabled. Enabled tools run without asking, so the settings say to add only trusted servers; tokens go to the provider with each request.
- **Context and compaction**: The model lists give each model's window (Anthropic `max_input_tokens`; the Codex list's `context_window` times `effective_context_window_percent`, and its `auto_compact_token_limit`) and prices (Anthropic's pricing page by display name; for OpenAI the selected model's documentation page gives window and prices, read with `requestUrl()` once a day by `loadModelDetails`, in the background after the first answer; `onModelDetails` then saves the settings and updates the ring). A list older than a day is loaded again at start. Each answer's usage (`TokenUsage`: cache reads and writes, Anthropic's compaction pass) goes through `AgentCallbacks.onUsage` into the conversation's `usage` (`agent/usage.ts`: last context, tokens in and out, estimated cost; an optional field of the chat file; Clear resets it). The ring in the chat header (`setUsage`) shows the context against the selected model's window; its details show tokens used, the cost (on the ChatGPT plan a Manage usage link instead) and *Compact now*. The compaction point is 80 % of the window by default (`defaultCompactThreshold`; the Codex list's own point; Anthropic at least 50,000); the *Compaction point* setting (`compactPercent`, or `compactTokens` for a model whose window is unknown; the *Chats* group in both settings paths: a slider from 50k to 100 % with the default marked and a token field) moves it (`compactThreshold`). Each request asks the provider to compact there: Anthropic `context_management` `compact_20260112` with the `compact-2026-01-12` beta where the model list has it; OpenAI and the Codex route `context_management: [{type: "compaction", compact_threshold}]`. The Codex route doesn't document it: a 400 to a request with it sends the request again without, and if that goes through the plugin stops asking until Obsidian restarts (`chatgptCompacts`). Anthropic compaction deltas carry final values (content and nullable encrypted_content), round-tripped verbatim; null/empty-content failed compactions are no-ops and do not mark a boundary. A provider-switch summary suppresses threshold re-summarization from stale usage. An answer's successful compaction marks its API message (`compaction`, with Anthropic's readable summary); requests send from there on (`afterCompaction`), another provider gets the readable summary first. Folder rules given before it count as not given (`instructionsGiven` on what is sent), so they come again. The plugin writes its own summary (`agent/summary.ts`, same model, an ordered transcript in chunks sized to 35% of the authenticated model window, folded into a rolling summary (a failure preserves the original history), with estimated tokens: about 3 ASCII characters or 1 other character per token; no tools; its tokens count in `usage`) before a turn whose last request passed the point where the provider doesn't compact (after the message passed its checks; a refusal before the provider restores the history from before the summary, `beforeTurn`; an edit or regenerate starts the count anew), once when another provider takes over an encrypted compaction, once per turn when a request is refused as too long, and on *Compact now*; it replaces the history as a user message with a `summary-` turn ID. The chat shows a quiet note (`errorKind: "compacted"`). There is no cap by count: what the last compaction covers leaves the API history (`fromLastCompaction`, before a turn and when saving; repeated encrypted compactions retain the raw prefix until a readable summary exists, including across provider/model/account changes), and turns before the last compaction can't be edited or answered again (`editableTurn`).
- **Long chats in the view**: A chat shows its last 20 turns (`PAGE_TURNS`, `pageStart`); scrolled within 400 px of the top (or when they don't fill the view) the 20 before them come in above (`loadEarlier`, `ChatContainer.prependMessages`, `setHasEarlier`), keeping the view in place. Rows off screen aren't laid out (`content-visibility: auto`, not on iOS, where Safari loses the scroll position); scroll anchoring is on only while the user reads back. Folded steps and tool details are built when opened.
- **Live voice**: Codex's voice service over WebRTC with client delegation (`src/voice/`), the way the Codex app's voice mode uses it. The voice model only talks; a delegation (`delegation.created`, with the request's text) runs the user's last words as a normal chat turn on the selected provider (`handleUserMessage` with `VoiceTurnHooks`), with a context line asking for a spoken answer and what was said before (`voiceTranscriptText`). Steps go back as silent notes, the answer as text to say (`delegation.context.append` on the `commentary` and `speakable` channels, at most 500 bytes each). A request during a voice turn steers it; `ask_user` there ends the turn with the question (`VOICE_ASK_RESULT`). The call is created with `requestUrl()` (`chatgpt.com/backend-api/codex/realtime/calls`, model `gpt-live-1-codex`, Codex's headers and voices; `src/voice/codex.ts`) with the ChatGPT account sign-in (`ChatGPTOAuthService`, the same Codex-client token and refresh as the ChatGPT provider; no second sign-in, no API key); audio and events go over WebRTC. The voice button shows only while that sign-in exists. On mobile the microphone goes off in the background and the call is replaced on the return or ends after 60 s. A call holds the screen on until it ends, however it ends (`releaseVoiceScreen`); ending turns the microphone off at once, before the call has closed. A spoken addition before the voice turn's loop started waits and runs next, as typed text does; a voice request refused before sending tells the voice model (`onError`) and takes the spoken rows before it along.

## Debug

Turn on **Debug log** in the settings to write each message as sent (with its context lines), the model's answers with their text and tool calls, each tool call with its input and result, errors, and in voice each data-channel event and what was said, to `<vault-config-dir>/plugins/chatting-with-ai/debug.log` (`src/debug.ts`). It includes the user's messages, never keys or tokens. The row's Copy and Clear buttons and the "Copy debug log" command get it off a phone.

Stream recovery safety: MCP-capable POSTs disable transport fallback after a lost response; absent headers do not prove absent external effects. Optional pendingTurn.remoteEffectsPossible prevents Continue after restart for an uncertain remote request. Continue requires the original visible user turn, retains its selection fingerprint, and re-reads MCP settings on each request.
